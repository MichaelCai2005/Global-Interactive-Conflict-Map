# Putting the map online

The site has two parts to host. Both read their settings from environment variables, so
the code doesn't change between your laptop and the web.

| Part | Where | Setting |
|---|---|---|
| Database (Postgres + PostGIS) | [Neon](https://neon.com) | — |
| Site: the API and the built frontend in one container (root `Dockerfile`) | [Render](https://render.com) (`render.yaml`), or Railway or Fly.io | `DATABASE_URL`, `PUBLIC_MODE`, `ADMIN_TOKEN` |

The API and the frontend are served from one address on purpose. Visitors sign in with a
cookie, and browsers increasingly block cookies sent to a different site, so a frontend
on Vercel calling an API on Render would leave people unable to stay signed in.

## What a public site may show

ACLED's license forbids publishing its events, so the hosted database never gets them.
`python -m app.publish copy` leaves out ACLED events, links to them and board nodes built
on them, and rebuilds the cell features and risk scores from what it copied. The API
backs this up in two ways. With `PUBLIC_MODE=true` it refuses to start if the database
holds ACLED data, and it refuses ACLED uploads even from an admin. UCDP (CC BY 4.0), GDELT
and the World Bank indicators can be republished with credit.

## 1. Create the database

1. Sign up at neon.com and create a project. Pick the region nearest your API host and
   Postgres 17, the same version you run locally.
2. On the project's dashboard, click **Connect** and copy the connection string with
   **connection pooling turned off** (the host has no `-pooler` in it). The copy needs a
   direct connection.
3. Turn it into SQLAlchemy's form by changing `postgresql://` to `postgresql+psycopg://`.
   Keep `?sslmode=require` on the end.

You don't need to create PostGIS yourself. The first migration runs
`CREATE EXTENSION postgis`, and Neon allows it on every plan.

## 2. Copy your data

Start your local Postgres, then from `backend/`:

```powershell
$env:TARGET_DATABASE_URL = "postgresql+psycopg://USER:PASSWORD@HOST/neondb?sslmode=require"
.venv\Scripts\python -m app.publish copy
```

The command migrates the target to the current schema and streams every table across in
one transaction, so a failed copy leaves nothing half done. It then rebuilds the features
and risk scores on the target and checks it holds no ACLED data. It won't overwrite a
database that already has events unless you pass `--replace`.

On 2026-10-21 a full copy took about 4 minutes into a local database and came to 979 MB
(689k UCDP and GDELT events). `--since 2018-01-01` came to 568 MB in under 2 minutes.
Neon's free plan holds 0.5 GB per project. Its paid Launch plan has no monthly minimum,
bills storage at about $0.35 per GB-month and compute by the hour, and shuts the
database down when nobody is using it. A full copy costs well under a dollar a month to
store.

Too big for the free tier? Copy less:

- `--since 2010-01-01` copies only events from that date on.
- `--without gdelt` leaves GDELT's news-based events out.
- `--with-workspace` also copies your watchlist and tasks, which stay local by default
  because they're personal notes.

`python -m app.publish check --url <url>` lists anything in a database that a public site
must not show.

## 3. Deploy the site

The root `Dockerfile` builds the frontend, then serves it beside the API from one
process (`backend/app/site.py`): pages at `/`, the API at `/api`. `render.yaml` describes
the service for Render.

1. Push the branch you want live to GitHub. Render deploys the blueprint's branch on
   every push.
2. On render.com: **New > Blueprint**, connect the GitHub repo, and pick the branch.
3. Render reads `render.yaml` and asks for the one secret it can't fill in itself:
   `DATABASE_URL`, the Neon URL from step 1 (direct, in `postgresql+psycopg://` form).
4. Click **Apply**. The first build takes a few minutes. The container runs the
   migrations, then starts.

The blueprint sets these environment variables:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The Neon URL, entered by you. |
| `PUBLIC_MODE` | `true`. Writes need a sign-in or the admin token, and the site won't start on ACLED data. |
| `ADMIN_TOKEN` | Generated by Render. Find it under the service's **Environment** tab. It's for uploads and the shared showcase boards; see below. |
| `SIGNUPS_OPEN` | `true`. Set it to `false` to stop new accounts while existing ones still sign in. |

Optional: `SESSION_DAYS` (how long a sign-in lasts, default 30) and `SECURE_COOKIES`
(cookies are HTTPS-only on a public site; set `false` only to test public mode over plain
HTTP).

Set these in the host's secret store, never in a committed file. With `PUBLIC_MODE=true`
the API refuses to start if `DATABASE_URL` still uses the development password
(`conflict`) from `docker-compose.yml`. `docker-compose.yml` is for local development
only. It binds the database and API to `127.0.0.1`, so they aren't reachable from the
network.

Leave `ANTHROPIC_API_KEY` unset. The Docker image doesn't install the Claude extra anyway,
so boards drafted on the server use the gazetteer.

Check it: `https://<your-site>/api/health` should return `{"status":"ok"}`, and the
address itself should show the map with **Sign in** and **Create account** at the top
right.

The blueprint uses Render's Starter plan, which stays awake. The free plan works too, but
it sleeps after 15 idle minutes, and the next visitor waits about a minute for it to
wake. To use your own domain, add it under the service's **Settings > Custom Domains**.

The container runs `alembic upgrade head` each time it starts. That's fine for one
instance. Before you scale to two or more, set `RUN_MIGRATIONS=false` and put
`alembic upgrade head` in the host's release step (Render calls it the **Pre-Deploy
Command**), so the migrations run once per deploy instead of in every instance at once.
Sign-in throttling counts attempts in each instance's memory, so with several instances
it is per instance.

### Accounts

Anyone can browse the map, the risk scores and the shared boards without an account.
To keep a watchlist, tasks, boards or saved searches, a visitor creates an account with
an email and a password. Each person sees only their own. Passwords are stored as scrypt
hashes. A sign-in is a random token in an HTTP-only cookie, and the database keeps only
its hash. Ten wrong passwords from one address in 15 minutes lock that address out for
the rest of the window, and one address can open five accounts an hour. A person can
change their password or delete their account, which deletes everything in it, from the
menu under their name.

There is no email step yet, so no email verification and no password reset by email. If
someone forgets their password, delete their row from `users` and they can sign up
again. Their boards and the rest go with it.

## 4. Keep it current

Two GitHub workflows update the hosted database. They run on GitHub's machines, not in
the API's container, so a long load never slows the site.

| Workflow | When | What it does |
|---|---|---|
| `update-hosted-data.yml` | Every night | Loads the last three days of GDELT events. Loading a day twice changes nothing, so a failed night or a late GDELT file is picked up the next night. Then it rebuilds those months' features and the risk scores and prunes live observations older than 90 days. |
| `update-ucdp.yml` | The 23rd of each month | Loads UCDP's monthly Candidate events (each month's file is posted around the 20th of the next), then rebuilds this year's features and the risk scores. It loads every file of the year again each time, so UCDP's corrections to earlier months arrive too. |

Both then check that nothing unpublishable arrived and report the database's size. To turn
them on:

1. On GitHub, open **Settings > Secrets and variables > Actions** and add a secret named
   `HOSTED_DATABASE_URL` holding the direct Neon URL from step 1.
2. Merge the workflows to the default branch, because GitHub only runs schedules from
   there. Use **Actions > Update hosted data > Run workflow** to run one now or to load a
   given GDELT day.

UCDP's yearly GED release usually comes out in June. Run **Actions > Update UCDP data >
Run workflow** with its version (e.g. `27.1`). The workflow loads it into the live
database in place, then rebuilds every month's features. The release replaces the
Candidate events for the years it covers. UCDP drops or recodes about one in seven of
them (271 of 1,912 for 2025), so the loader deletes the ones the release left out. Don't
use `python -m app.publish copy --replace` for this. It empties the hosted database
first, so boards and accounts made on the site would be lost.

### Watching the size

Neon's free plan holds 0.5 GB. GDELT grows the database a little every night, and UCDP
adds a few thousand events a month. Each run's last step logs the database's size and its
five largest tables, and puts a warning in the run summary once the database passes
450 MB. On a paid plan, raise that line with a repository variable `DB_SIZE_WARN_MB` (same
settings page, **Variables** tab). To check by hand:

```powershell
.venv\Scripts\python -m app.publish size --url "postgresql+psycopg://..." --warn-mb 450
```

If it gets close, copy a smaller window again with `copy --since` or `--without gdelt`
(step 2) before anyone has an account, or move to Neon's Launch plan.

## 5. Backups

Neon keeps every change for a restore window: 6 hours on the free plan, 1 day by default
on paid plans (up to 7 days on Launch, 30 on Scale). To undo a bad load or migration
within that window, open the project's **Backup & Restore** page and restore the branch to
a time before it. Neon makes a backup branch of the old state first, so a restore can be
undone too.

Most of the database can be rebuilt without a backup. Events come back from the source
files (`python -m app.publish copy` from your local database, or the workflows above),
and features and risk scores are rebuilt from the events. What can't be rebuilt is what
people make on the site: accounts, boards, saved searches, watchlists and tasks. The
free plan's 6 hours won't save those from a mistake noticed the next day, so take your
own copy now and then with the local Postgres's `pg_dump` (the same version as Neon's):

```powershell
& "$env:LOCALAPPDATA\conflict-map\pgsql\bin\pg_dump.exe" --format=custom `
  --file "conflict-map-$(Get-Date -Format yyyy-MM-dd).dump" `
  "postgresql://USER:PASSWORD@HOST/neondb?sslmode=require"
```

Use the plain `postgresql://` URL here, without `+psycopg`. `pg_restore --clean --dbname
<url> <file>` puts a dump back. Keep the dumps off GitHub, because they contain account
emails and password hashes.

## Changing data on the live site

Reads are open to everyone. A signed-in person changes only their own watchlist, tasks,
boards and saved searches. Everything else (uploads, and the shared boards that every
visitor sees, those without an owner) needs the admin token:

```bash
curl -X POST https://<your-site>/api/boards/draft   -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json"   -d '{"url": "https://..."}'
```

With no `ADMIN_TOKEN` set, a public deployment refuses all of these. A local setup with
no token stays open as before, and its watchlist, tasks and boards are the shared ones.
Sign in locally and you get a personal workspace beside them.

`python -m app.publish copy` copies only the shared boards, watchlist and tasks, never
accounts or anyone's own data. It also refuses to overwrite a database that has accounts,
because emptying it would delete what people saved. Once the site has users, update it in
place with the workflows in step 4.
